# stage-3 — Регистрация ограниченных поправок входа

Статус: зарегистрировано на этапе 3 по итогам проверки R0. Внешняя нормализация входа — **не** самостоятельный успех агента; она лишь устраняет противоречия входных документов, необходимые для согласованности плана. Прежние оценки и gate авторской сдачи этапа 2 не пересматриваются.

Допускаются только поправки **I201** и **I202** ниже. Прочие обнаруженные противоречия входа фиксируются отдельно в §4 и не исправляются молча.

---

## 1. I201 — strong ETag набора grants в контракте чтения

| Поле | Значение |
|---|---|
| **ID** | I201 |
| **Исходное противоречие** | `replaceIntegrationGrants` (PUT `/api/v1/integrations/{integrationId}/grants`) требует `If-Match` (428/412), но контракт чтения `listIntegrationGrants` (GET) не описывает получение ETag для этого заголовка. Без документации ETag условие 428/412 невыполнимо для клиента и не тестируемо по контракту. |
| **Требование** | Документировать выдачу сильного ETag текущего набора grants в ответах чтения и успешного изменения, включая пустой набор. Сохранить требования 428/412 и актуальность прав (D207) без изменений. |
| **Точная поправка** | В `docs/openapi.yaml` к ответу `_PageIntegrationGrant` (используется и GET 200, и PUT 200) добавлен заголовок ответа `ETag` с описанием: сильный ETag текущего набора grants (I201), обязателен для `If-Match` в `replaceIntegrationGrants`, выдаётся и для пустого набора. |
| **Затронутые документы** | `docs/openapi.yaml` (компонент responses → `_PageIntegrationGrant`). |
| **Источник** | Этап 2 (`stage-2 §7`: ETag/If-Match для изменяемых настроек; §7.2 grants PUT). |
| **Статус внешней нормализации** | Зарегистрировано на этапе 3; применено минимально в OpenAPI. |

---

## 2. I202 — значение и жизненный цикл `CatalogItem.asOf`

| Поле | Значение |
|---|---|
| **ID** | I202 |
| **Исходное противоречие** | В `docs/openapi.yaml` описание `CatalogItem.asOf` — «момент заполнения кеша каталога (T06/T09)», что противоречит утверждённому `stage-2 §6.1`: момент фиксируется **перед началом чтения данных из БД** и **не обновляется при записи в кеш**; срок свежести (30 с) не начинает отсчитываться заново после позднего заполнения. |
| **Требование** | Согласовать описание OpenAPI с `stage-2 §6.1`. `asOf` отражает начало чтения данных, не момент записи в кеш; поздний cache-fill не продлевает жизнь старому снимку. |
| **Точная поправка** | В `docs/openapi.yaml` описание `CatalogItem.asOf` заменено на: «момент, зафиксированный перед началом чтения данных из БД; не обновляется при записи в кеш; срок свежести не отсчитывается заново после позднего заполнения (stage-2 §6.1, I202)». |
| **Затронутые документы** | `docs/openapi.yaml` (schema → `CatalogItem.asOf`). |
| **Источник** | Этап 2 (`stage-2 §6.1`, T06/D209). |
| **Статус внешней нормализации** | Зарегистрировано на этапе 3; применено минимально в OpenAPI. |

## 3. Синхронизация затронутых документов

- `docs/openapi.yaml` — минимально изменён по I201 и I202 (см. §1–§2). Других изменений OpenAPI не вносится.
- `docs/stage-2.md` — правок не требует: §6.1 уже задаёт корректную семантику `asOf` (источник I202); ETag/If-Match и актуальность прав уже согласованы (источник I201).
- `docs/stage-3.md` — ссылается на I201 (в задаче настройки интеграций/grants) и I202 (в задаче кеша каталога).

## 4. Прочие обнаруженные противоречия входа (зафиксированы, не исправляются молча)
