## 1. Стек и состав проектов (T01–T02)

### 1.1 Стек (фиксируется, версии — см. §1.4)
**.NET 10 / ASP.NET Core**, **EF Core 10 + Npgsql**, **PostgreSQL 17**, **Valkey 9**, приватное **S3-совместимое хранилище**. PostgreSQL не заменяется другой БД, Valkey — памятью, S3 — локальной ФС.

### 1.2 Минимальные проекты и границы
```
Motiva.sln
├── src
│   ├── Motiva.Domain          # чистые доменные правила, агрегаты, календарь периодов, диапазоны
│   ├── Motiva.Application     # use case, оркестрация, порты, авторизация действий
│   ├── Motiva.Infrastructure  # PostgreSQL (EF/Npgsql), Valkey, S3, генератор CSV, JWT-провайдер
│   ├── Motiva.Api             # ASP.NET Core: маршрутизация, DTO, middleware, composition root
│   └── Motiva.Worker          # фоновые процессы: выписки, очистка S3, публикация рейтинга
└── tests
    ├── Motiva.Tests.Unit            # домен/application (моки портов)
    ├── Motiva.Tests.Integration     # PostgreSQL 17, Valkey 9, S3 (функциональные, HTTP/contract, persistence)
    └── Motiva.Tests.Architecture    # архитектурные и отрицательные проверки
```
Дополнительный `Motiva.Contracts` допустим только при обоснованной необходимости (напр., разделение DTO между Api и Integration-тестами); по умолчанию DTO живут в Application/Api.

### 1.3 Зависимости и сборка
`Api → Application`, `Api → Infrastructure`, `Worker → Application`, `Worker → Infrastructure`, `Infrastructure → Application` (порты), `Application → Domain`, `Infrastructure → Domain`. Domain не зависит от EF/HTTP/SDK; Application — от инфраструктурных реализаций. Composition roots — в `Api` и `Worker`. Endpoint/worker orchestration не обращаются напрямую к `DbContext`/Npgsql/S3 SDK (только через use cases и порты). DTO не являются EF-entities; `IQueryable` не покидает хранилище. Внутри проектов — группировка по предметным функциям (Каталог, Выполнение, Кошелёк, Рейтинг, Экспорт, Доступ).

### 1.4 Фиксация версий и стиль
- SDK, пакеты и образы фиксируются; lock-файлы (`packages.lock.json`, Compose-образы с тегами), без плавающего `latest`. Предложенные версии — проектные, не подтверждённые исполнением на этом этапе.
- Миграции рассчитываются на PostgreSQL 17, включая обновление существующей БД.
- Локальный S3-провайдер выбирается и обосновывается при реализации (кандидат — MinIO); совместимость «со всеми провайдерами» не обещается.
- Стиль по `.editorconfig`: nullable, явная доступность, PascalCase типов/методов, camelCase параметров, `_camelCase` приватных полей, async I/O + `CancellationToken` по цепочке. Нет `.Result/.Wait()`, глобального подавления предупреждений и необоснованной смены стиля.
- Проверки, обязательные для use case (авторизация, валидация, бизнес-повторы), выполняются в Application-входах, а не только в Web middleware — они сохраняются при вызове из Worker и функциональных тестов (D207/D211).

## 2. Договор JWT (T03)

### 2.1 Формат
| Поле | Требование |
|---|---|
| `iss` | `motiva-benchmark` |
| `aud` | `motiva-api` |
| Алгоритм | только HS256 в локальном профиле |
| `sub` | постоянная идентичность инициатора |
| `companyId` | UUID компании |
| `actorType` | `user` либо `service` |
| `masterId` | положительный Int32, обязателен для `user` |
| `role` | `Employee`; дополнительный `Admin` для администратора |
| `exp`, `nbf` | проверяются; clock skew ≤ 30 с |

- Владелец определяется записью кампании, а не ролью `Owner`. `service` не имеет кошелька и не получает пользовательские полномочия.
- Обязательные identity-claims проверяются на отсутствие, дублирование и противоречия; представление нескольких ролей настраивается явно. Старые `master_id/company_id` и роли `owner/integration` не используются.
- Ключ: `Auth__Issuer`, `Auth__Audience`, `Auth__SigningKeyBase64`; подпись проверяется по **Base64-декодированным байтам**. Секреты/JWT/signed URLs не коммитятся и не логируются.
- Токены выпускаются вне Motiva (`.NET SDK`, `dotnet user-jwts`). Bootstrap: только начальные компании и активный Admin — через доверенные use cases (T03); остальное — через административный API.
- Корпоративная смена роли Admin требует нового токена; мгновенный отзыв JWT, SSO и refresh tokens вне задачи. Актуальная блокировка бизнес-профиля и grants обязательна и реализуется через `IAuthorizationContext` (D207).

## 3. Модель данных (D210)

Диапазоны (T05): суммы/цели/delta/очки ≤ 10⁹ (INTEGER); балансы и бюджеты ≤ 10¹⁵ (BIGINT/NUMERIC(38,0)); `masterId` — положительный Int32; `companyId` — UUID. Примечания D210:
- `wallet_balance.balance` и `budget.remaining` — BIGINT, покрывают три начисления по 10⁹ и лимит 10¹⁵. `challenge_score`/`stream_score` — BIGINT (накопительные суммы нескольких входных значений по 10⁹). Отдельное входное значение (цель/delta/сумма/очки) ≤10⁹; накопительная сумма ≤10¹⁵.
- `progress.value ≤ task.goal` — доменное правило (B14d), в БД реализуется триггером, а не обычным CHECK (межтабличная ссылка).
- **Регистронезависимая уникальность всех кодов** (resource, campaign, stream, task, achievement) — expression index `UNIQUE(parent_id, lower(code))`.
- **Набор ресурсов кампании** и **позиции награды задания** нормализованы в `campaign_resource`/`task_reward` (FK→resource) — принадлежность компании обеспечивается FK, а не JSON. JSON допустим для аудитории-тегов с проверкой принадлежности в Application.
- **Grants (D210):** сочетания полей по kind: progress — `campaign_id` обязателен, `resource_id`/`purchase_system_id` недопустимы; accrual — `campaign_id`+`resource_id` обязательны, `purchase_system_id` недопустим; spend — `purchase_system_id`+`resource_id` обязательны, `campaign_id` недопустим. Отсутствие области не означает wildcard. Уникальность nullable-колонок — через `COALESCE(...,0)` (обычный UNIQUE не считает два NULL равными).
- **Черновик и история (D210):** B18 не запрещает выделение бюджета до публикации. Удаление черновика не уничтожает операции/движения/аудит: физическое удаление допустимо только при отсутствии таковых; иначе черновик переводится в логическое `deleted` с сохранением истории. Незаявленный запрет выделения не вводится.
- `challenge` не имеет ограничения «один на стрим» (B31 не задаёт его).

### 3.3 Идемпотентность и восстановление ответа
`operation_request` хранит канонический payload и исходный результат; уникальный индекс `operation` — только защита от дублей. После изменения ресурса повтор бизнес-номера возвращает прежний ответ из `operation_request` (сохранённые ID, статус, представление), а не пересчитывает.

### 3.2 Бюджеты по ресурсам, единый кошелёк, движения
- **Бюджет** `budget.remaining` на пару (кампания, ресурс): `remaining = Σ выделений − Σ проведённых начислений + Σ успешных отмен этих начислений` (B19a). Выделение только админом (B18), каждая — операция `budget_allocation` + `audit_entry`.
- **Единый кошелёк** `wallet_balance(wallet_id, resource_id)`: одинаковый ресурс из разных кампаний — один баланс (B22b).
- **Движения** `wallet_movement(delta, balance_after)` на каждое изменение, со ссылкой на операцию; отклонённые операции не порождают движения (B28c); `balance_after` объясняет каждый баланс.

## 4. Механизмы инвариантов и протоколы (D203)

Обозначения: **DB** — ограничение/триггер БД; **TX** — транзакция; **APP** — проверка Application/Domain; **WK** — worker. Для всех экономических операций обязателен законченный протокол (см. ниже), а не только «транзакция + FOR UPDATE».

### 4.1 Общие принципы
Различаются моменты: **приход HTTP** (вход), **системный момент принятия** (назначается `TimeProvider`, `accepted_at`), **commit**, **отправка ответа**. Экономический эффект фиксируется в одном согласованном наборе записей внутри одной транзакции (B17); перенос эффекта в несогласованный последующий процесс исключён. Lock/isolation level не навязываются, требуется законченный механизм по каждому пути (§4.2–4.5). Отсутствующие строки обрабатываются upsert с `ON CONFLICT`.

### 4.2 Принятие события (прогресс/завершение/награда/рейтинг)
Транзакция приёма события `E` (сотрудник, задание, increase>0, source_event_no). **Единый порядок** (согласован с §5.1/D201):
1. **Идентичность и права:** интеграция имеет grant progress по кампании задания; активность сотрудника (актуальный источник).
2. **Сохранённый результат:** вставка `event` по `UNIQUE(company_id, source_id, source_event_no)`; при конфликте — повтор: вернуть прежний результат без переоценки (период/награда/архив не пересчитываются).
3. **Сериализация нового события:** захватить `FOR UPDATE` все строки `challenge` этого стрима в порядке `id`, без предварительного отбора по времени или состоянию; удерживать до commit. Захват предшествует `accepted_at`, `progress` и экономическим блокировкам (§4.7).
4. **`accepted_at`, предусловия и период:** после захвата всех `challenge` единственный системный `accepted_at` назначается `TimeProvider` в этой транзакции. По нему проверяются сроки кампании и определяется период задания через `ICompanyCalendar`; проверяются аудитория кампании и задания (актуальный источник), кампания published, задание и стрим не архив. При отказе транзакция откатывается, номер события не занят. Последующие ожидания блокировок и задержка ответа не меняют `accepted_at`.
5. `FOR UPDATE` строки `progress(employee, task, period)` (upsert при отсутствии); `credited = min(goal − old, increase)`; обновить `progress`; сохранить `event.sent_increase`, `event.credited_increase`.
6. Если достигнута цель и нет `completion`: вставить `completion` (unique не даёт дубля); добавить очки в `stream_score` (read-modify-write с FOR UPDATE); проверить вехи стрима → `achievement_grant` (upsert, `UNIQUE(employee, achievement, season)`); решение о награде §4.3.
7. **Рейтинг:** счёт обновляется на `credited_increase` **каждого нового принятого события** (не только завершения). Первое событие с нулевым `credited_increase` тоже создаёт участника (`challenge_score` строка с 0). Из уже заблокированных на шаге 3 челленджей обновляется каждый, чей интервал `[start,end)` содержит `accepted_at`; итог `final` не изменяется (§4.5).
8. Commit; отправка ответа после commit.

**Закрытие путей (D203):**
- Два события одного задания за цель: `progress` FOR UPDATE сериализует; `completion` unique гарантирует одно завершение; второе credited=0.
- Два завершения разных заданий одного стрима: `stream_score` read-modify-write с FOR UPDATE не теряет очки.
- Пересечение нескольких вех: все положенные `achievement_grant` в одной транзакции; `UNIQUE` предотвращает повтор.
- Одно достижение через разные стримы/кампании в сезоне: `achievement_grant` keyed (employee, achievement, season) — один раз (B30).
- Создание первого баланса ресурса: upsert `wallet_balance` (ON CONFLICT); первый `wallet_movement` создаёт строку.

### 4.3 Пакетная награда (B20) и конкуренция за последний остаток
В той же транзакции приёма события, **после захвата замков порядка §4.7**: `FOR UPDATE` по всем `budget` позициям пакета; проверить каждый `remaining ≥ amount`; все → списать все позиции (операция `task_reward` + `operation_line` + `wallet_balance` += + `wallet_movement`), `posted`; иначе — `declined` (причина «недостаточно бюджета»/«ресурс недоступен»), без движений. Решение окончательное (B20c). Архивный ресурс → пакет declined, выполнение учитывается (B07e). Равенство остатка сумме достаточно (B19).

### 4.4 Полные протоколы операций (списание, начисление, выделение, возврат, отмена)
Общий шаблон для каждого вида: защищаемые записи → отсутствие строки (upsert) → чтение актуального значения (FOR UPDATE) → изменение → сохранение результата + `operation_request` → обработка конфликта (повтор/одна отмена). Порядок захвата — §4.7.

- **Списание** (`spend`): проверка системы покупок, ресурса в принимаемых, активности получателя; `FOR UPDATE wallet_balance`; достаточность → posted, иначе declined (B23e); трата не возвращает в кампанию (B23f); `basis` обязателен.
- **Ручное начисление** (`manual_accrual`, B21): получатель активен и участник действующей кампании; полномочия владельца/Admin или grant accrual интеграции (RA4 не влияет — активный получатель); `FOR UPDATE budget(campaign, resource)`; достаточность → списать бюджет, `wallet_balance` +=, движение, posted; иначе declined (B21e). Прогресс/достижения/рейтинг не меняются (B21d).
- **Выделение бюджета** (`budget_allocation`, B18): только Admin; `FOR UPDATE budget(campaign, resource)` (upsert при первом выделении); только увеличение; `remaining += amount`, операция + `audit_entry`, posted.
- **Возврат списания** (`spend_refund`, B27): Admin либо та же система покупок с актуальным grant spend на ресурс и систему; `FOR UPDATE original_operation` (§5.2): если уже отменён → 409; полная сумма в исходный кошелёк, без бюджета; posted (одна успешная отмена).
- **Отмена начисления** (`accrual_cancellation`, B26): Admin, либо владелец исходной кампании при активном получателе (заблокированный — только Admin, RA4); полный пакет `operation_line`; `FOR UPDATE original_operation` + всех затронутых `wallet_balance`; нехватка хотя бы одного баланса → declined целиком; успех — возврат всех позиций в исходные бюджеты, posted; прогресс/очки/достижения/рейтинг не отзываются (B26d).

### 4.5 Публикация, редактирование, финализация челленджа, архив
- **Публикация** (Draft→Published): атомарный переход; валидация заданий/ресурсов/вех/челленджей. **Согласованная защита настроек:** валидация черновика и переход в published выполняются в одной транзакции (нельзя проверить черновик, затем опубликовать другой транзакцией и сохранить запрещённое изменение). Поля делятся: до публикации (сезон, сроки, состав заданий, цели, периодичность, награды, очки, правила рейтинга, ресурсы); после публикации (название, описание, аудитория, владелец — B09f); никогда (всё перечисленное в B09e). Иные изменения после публикации — 409.
- **Аудит доступа:** изменение аудитории/тегов/владельца/блокировки сразу влияет на новые обращения; проверка доступа к новому прогрессу и фильтрация **самой выдачи** каталога/рейтинга читают актуальный источник (D209), не кеш.
- **Архив ресурса:** архивирование и новое начисление/списание согласуются в одной транзакции (архивный ресурс нельзя начислять/тратить, B07b); архив не мешает полной отмене прежней операции (B07d).
- **Финализация челленджа** (B33): событие и финализация сериализуются через `FOR UPDATE` на строке `challenge`. Событие сначала захватывает все `challenge` стрима, затем фиксирует `accepted_at` (шаги 3–4 §4.2); замки удерживаются до commit. Финализатор в **READ COMMITTED** захватывает тот же замок и проверяет `TimeProvider.now ≥ end`; до end финализация запрещена. Затем **отдельным запросом после захвата замка** читает события с `start ≤ accepted_at < end`, фиксирует итог и `challenge=final` в той же транзакции. Этот запрос видит commit всех ранее принятых событий интервала, включая событие с задержанным ответом; ожидавшее замок до конца соревнования событие получает время только после захвата и при `accepted_at ≥ end` не входит в итог. После `final` итог неизменяем; повтор события и отмена награды его не меняют (B33c–e). Очки/награды на счёт не влияют (B31c).
- **Публикация рейтинга** (T06): после `final` итог публикуется в Valkey не позднее 5 с.

### 4.7 Единый порядок захвата и изоляция (D202/D203)
Для всех путей, затрагивающих бюджет и кошелёк, фиксируется **единый порядок захвата**, чтобы исключить взаимную блокировку (начисление идёт бюджет→кошелёк, отмена — тоже бюджет→кошелёк через тот же порядок, а не противоположный):
1. При отмене — строка `original_operation` первой.
2. При событии — все `challenge` стрима (по id), затем `progress` и записи завершения/очков/достижений по §4.2; до экономических блокировок.
3. Строки `budget` (по `campaign_id, resource_id`, отсортированно).
4. Строки `wallet_balance` (по `wallet_id, resource_id`, отсортированно).

Выбранная изоляция: **READ COMMITTED + явные блокировки строк (SELECT ... FOR UPDATE)** по порядку выше, включая финализацию челленджа; для снимка выписки — **REPEATABLE READ** (MVCC-снимок). У финализатора чтение результата выполняется отдельным запросом после ожидания замка: REPEATABLE READ сохранил бы снимок первого запроса до ожидания ([PostgreSQL 17](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-REPEATABLE-READ)). Ограниченное повторение всей транзакции при сериализационных конфликтах/deadlock: retry до N раз в рамках общего deadline (§6.4); частичного результата не остаётся (одна транзакция на операцию, B17). Расписания проверяются для: бюджет→кошелёк (начисление), кошелёк→бюджет заменён единым порядком (отмена использует §4.7), пакетные позиции — по sorted order.

## 5. Повторы, одна успешная отмена, числа (T05/D201/D202)

### 5.1 Два механизма повторов и отображение бизнес-номера
1. **Бессрочный (B16/B24):** бизнес-номер → неизменяемый результат, включая экономический отказ. Область события: `(company, source_id, source_event_no)` (B16). Область операции: `(company, initiator_key, kind, source_no)` (D201).
2. **Транспортный (создание настроек):** `Idempotency-Key` ≥ 24 ч; scope — (компания, проверенный инициатор, операция/целевой ресурс, ключ).

**Отображение `Idempotency-Key` (D201).** Для экономических операций (spend, manual-accrual, budget-allocation, accrual-cancellation, spend-refund) заголовок `Idempotency-Key` **является бессрочным бизнес-номером источника** (B24): область `(company, initiator_key, kind, idempotency_key)`, хранится бессрочно. Для события — `sourceEventNo` (B16). Для создания настроек — транспортный ключ ≥24 ч. Один заголовок полностью реализует бизнес-договор; дублирующий ключ не вводится. Бессрочная защита не подменяется 24-часовой записью.

**`initiator_key` (D201).** Представление `"{actor_type}:{actor_id}"`, где `actor_type ∈ {user, service}`. `user:7` и `service:7` — разные инициаторы. Смена роли Employee/Admin и переход между маршрутами не меняют `actor_type`/`actor_id` для одной личности → не создают вторую копию бизнес-операции. Обязательные identity-claims из JWT проверяются на дублирование/противоречия (T03).

**Сохранение существенных данных запроса (D201).** Таблица `operation_request(operation_id, initiator_key, kind, source_no, canonical_payload, result, http_status, response_view)` хранит нормализованные существенные данные запроса (канонический JSON, независимый от порядка полей и позиций), исходный результат и HTTP-представление. Это позволяет восстановить прежний ответ после изменения ресурса (см. §3.3), а не полагаться только на уникальный индекс.

**Порядок проверок (единый, устраняет противоречие §4.2/§5.1):** актуальная идентичность → проверка grant и предусмотренной активности → **поиск сохранённого результата** (и сравнение запроса с каноническим) → **только для нового действия** — бизнес-предусловия (сроки, аудитория, опубликованность, архив, бюджет). Повтор принятого события после архива или окончания кампании возвращает **прежний результат** (не отклоняется как новый). Отзыв grant/владения и активность не обходятся и проверяются до возврата сохранённого результата.

**Конкурентный дубликат и неопределённый commit.** Параллельный повтор может ограниченно ждать (deadline, §6.4) либо получить 503/Retry-After; последующий повтор восстанавливает результат. При неопределённом исходе после commit повтор не выполняет эффект без проверки уже сохранённого результата в `operation_request`. Повтор возвращает прежние ID, HTTP-статус и представление; тело при повторе не меняется флагом `idempotent=true`, если первоначально было `false`. GET показывает актуальное состояние. Ошибки доступа/валидации/временной недоступности не сохраняются как успешная обработка.

### 5.2 Одна успешная отмена (D202)
Механизм: все попытки отмены сохраняются как операции (`accrual_cancellation`/`spend_refund`) с результатом `posted`/`declined`. Успешных отмен на один оригинал — не более одной, через **частичный уникальный индекс**:
`UNIQUE(original_operation_id) WHERE result='posted' AND kind IN ('accrual_cancellation','spend_refund')`.

**Защита оригинала и откат движений (D202).** У исходной операции поле `cancellation_state ∈ {none, posted}` (обновляется в той же транзакции, что и успешная отмена). Протокол отмены:
1. `FOR UPDATE` строки `original_operation` (порядок захвата — §4.7).
2. Если `cancellation_state = posted` → **конфликт состояния**: 409, движений не выполняется, результат первой отмены не трогается.
3. Проверить достаточность баланса по всем позициям пакета (`operation_line`): недостаток → **экономический отказ**, 201 `OperationOutcome.status=declined`, движений нет.
4. Иначе — атомарно: провести возврат всех позиций (движения), выставить `cancellation_state=posted`, сохранить операцию-отмену `posted`.
5. Повтор прежнего номера (`operation_request`) → возврат прежнего результата (declined или posted).

**Различаемые случаи и их HTTP-статусы (согласовано с OpenAPI):**
| Случай | Код |
|---|---|
| Экономический отказ (недостаток средств) | 201 `OperationOutcome{status:declined}` |
| Конфликт состояния (оригинал уже успешно отменён) | 409 `conflict` |
| Replay прежнего номера | 201 с прежним `OperationOutcome` (нет повторного эффекта) |

Разбор (D202): (1) отказ из-за потраченного B → declined без движений; (2) последующее пополнение B; (3) успешная отмена новым номером → posted (partial index захватывает, движения проведены); (4) повтор старого отклонённого номера → прежний declined; (5) конкурирующие успешные отмены → `FOR UPDATE` оригинала сериализует, одна posted, вторая 409 (движения не дублируются, первая не откатывается). Причина, оригинал, номер и полный состав (`operation_line`) — в API и модели.

### 5.3 Числа и время (T05)
- `masterId` положительный Int32; `companyId` UUID. Внутренние суррогатные `bigint` с явным отображением.
- Коды ASCII `[A-Za-z0-9_-]{1,40}`; **регистронезависимая уникальность для всех кодов** (resource, campaign, stream, task, achievement) через expression index `UNIQUE (parent_id, lower(code))` (D210).
- Названия 1–200; описания ≤2000; теги `[a-z0-9-]{1,32}`; внешние номера 1–100 ASCII (регистрозависимые).
- Отдельные входные значения (цель/delta/сумма/очки) ≤10⁹; **накопительные суммы** (балансы/бюджеты/`challenge_score`/`stream_score`) — BIGINT ≤10¹⁵ (D210). Точная целочисленная арифметика с проверкой переполнения; нарушение диапазона — 400 без частичного эффекта.
- Внешние даты с UTC offset, выход UTC; тестовое время через `TimeProvider`, без production HTTP-переключателя часов.

### 5.4 RA4 в механизмах
Отмену/возврат **заблокированного** получателя выполняет только Admin (RA4). Для активного — владелец (своя кампания) / admin / та же система покупок (B27). Проверка активности и полномочий — в Application-входе (D207).

## 6. Конкуренция, кеш, экспорт (T06–T07/D208/D209)

### 6.1 Кеш (T06/D209)
**Каталог (неперсональный):** ключ `catalog:{company}:{season}`; значение — полная структурная выборка кампаний/стримов/заданий/ресурсов без учёта прав; поле `asOf` фиксируется перед началом чтения данных из БД и не меняется при записи в кеш; срок годности (TTL) = 30 с (обязательное T06). **Чтение:** возраст = `now − asOf`; если возраст > 30 с — miss → перечитать из БД, перезаполнить. **Запись:** write-if-`asOf`-newer (атомарно) — старый снимок не перезаписывает свежий; TTL ограничен остатком до `asOf + 30 с`, просроченный снимок не записывается; повреждённое значение → miss; отказ Valkey → ограниченное ожидание и PostgreSQL fallback. **Фильтрация прав (D209):** кеш хранит полные данные; **выдача** каталога фильтруется по актуальным правам (аудитория кампании и задания, теги, блокировка, владелец) из `IAuthorizationContext` на момент чтения — неперсональный кеш не становится источником устаревших прав. `asOf` включается в ответ каталога (контракт `CatalogItem.asOf`).

**Live leaderboard:** ключ `lb:{challengeId}:top:{limit}`; TTL = 5 с (обязательное T06), `asOf` в ответе; время `asOf`, write-if-newer и остаточный TTL определяются так же, как для каталога, с пределом 5 с; чтение — проверка возраста, miss → пересчёт из БД. **Финальный результат** — авторитетные неизменяемые данные `challenge_score` (finalized), а не текущее содержимое кеша. Выдача `top` фильтруется по актуальной доступности читателя; собственное место — отдельная операция по актуальным данным (не кеш).

Кеш не используется для принятия решений по деньгам/правам/активности (B05/B19/B22).

### 6.2 Снимок выписки (D208/B36)
Состав фиксируется **при первом успешном начале формирования**:
1. `POST /statements` → `statement(state=pending)`; состав не фиксируется.
2. Worker: транзакция с **MVCC-снимком** (repeatable read); выборка движений по фильтрам в этом снимке; список `movement.id` сохраняется в `statement_data(snapshot_id, ids)`; `statement` переходит `pending→forming` атомарно (единственный переход, фиксирующий снимок) и присваивается владелец попытки (lease).
3. Поздний commit с ранним `created_at` не попадает: состав определяется MVCC-видимостью снимка, не только timestamp-фильтром.
4. Повтор/второй worker читает `snapshot_id` — выборка не переснимается, состав переиспользуется (B36c).
5. Crash до фиксации снимка: `statement` остаётся `pending`/`error`; успешного начала не было — повтор формирует заново. Crash после фиксации: повтор с тем же `snapshot_id`.
6. Формирование потоковое; 100 000 строк ≤ 120 с на исправном стенде (T07).

### 6.3 Жизненный цикл S3, workers и cleanup (D208)
**Владение попыткой.** `statement_attempt(statement_id, owner_worker_id, lease_expires_at)`. Worker берёт попытку (CAS: свободная или истёкший lease), обновляет lease. Зависшее `forming` с истёкшим lease перехватывается другим worker, **но** использует тот же `snapshot_id` (состав не переснимается). Прежний worker после перехвата проверяет владение (lease/owner) перед публикацией и не публикует при утрате.

**Атомарный переход Ready (D208).** Готовность публикуется **условным обновлением**:
`UPDATE statement SET state='ready', file_ref=:obj WHERE id=:id AND state='forming' AND owner_worker_id=:me`.
Это CAS: удаление (state=deleted), повторный перехват и публикация взаимоисключаются. `Ready` ссылается на проверенные байты и выставляется только если объект существует и целостен (content-md5). **Удаление между проверкой `state != deleted` и присвоением Ready:** CAS не проходит при state=deleted, поэтому Ready на удалённую выписку не ставится; удаление выигрывает. Поздняя загрузка старым worker после удаления: объект загружен, но CAS Ready не проходит → объект помечается на уборку, экспорт не воскресает (B37b).

**Уборка (cleanup).** Объекты сохраняемого `snapshot_id` не удаляются у неудалённой выписки, в том числе при истёкшем lease или ожидании повторной попытки: тот же объект нужен восстановлению. Cleanup удаляет объекты и незавершённые загрузки выписок со `state=deleted` не позднее 10 минут после восстановления зависимостей; повторные проходы убирают поздние загрузки. Гонка «cleanup удалил объект → worker публикует Ready» исключена: cleanup работает только после необратимого deleted, при котором CAS Ready уже не проходит; истечение lease само по себе не разрешает удалять общий объект.

**Защита байтов от перезаписи (D208).** Объект с детерминированным ключом = `snapshot_id`; загрузка выполняется **conditional write** (например, `If-None-Match: *` / put-if-absent в выбранном S3-профиле, MinIO): повторная запись в один ключ не перезаписывает существующий проверенный объект. При восстановлении объект определяется безопасно: проверка существования по ключу + проверка `content-md5`/метаданных; при несовпадении — перезагрузка из `statement_data`. Долгие S3-операции выполняются вне транзакции основной экономики.

### 6.4 Фоновые процессы, надёжность, наблюдаемость (T07)
- Два API и два worker; корректность не зависит от process-local lock или Valkey-lock (сериализация — в PostgreSQL, §4.5/§4.7).
- **Общий deadline** на операцию (не сумма неограниченных попыток): HTTP/DB запрос — суммарно 10 с на все retry, после исчерпания бюджета — 503/Retry-After; Valkey — 200 мс/2 попытки в рамках 500 мс; S3 — 10 с на операцию. Поведение при неопределённом commit — проверка исхода (§5.1). Значения — проектные параметры, не ослабляющие обязательные 30/5 с и 5 с финализации (T06/T07).
- Structured logs, trace/correlation ID, метрики запросов/повторов/очереди. Недоступность PostgreSQL → ограниченный 503, не ложный успех. Readiness отражает возможность основной работы; liveness не падает только из-за внешней зависимости. Отказ S3 не блокирует основную экономику.

## 7. REST и OpenAPI (T04/D204/D205/D206)

### 7.1 Принципы
- **Без action-путей** (`/publish`, `/archive`, `/cancel`, `/spend`, `/refund`, `/execute`). Изменения настройки — PATCH ресурса; отмены/возвраты — отдельные ресурсы (`accrual-cancellations`, `spend-refunds`); состояния кампании/ресурса/стрима/задания — поле `status` при PATCH.
- Статусы: создание — **201 + Location**; чтение — 200; удаление — 204.
- **Экономический отказ корректной операции — сохранённый `Declined`, 201, та же схема результата, что `Posted`** (наблюдаемо через один контракт `OperationOutcome{status: posted|declined}`), не ProblemDetails (D206).
- Ошибки: 401 (неверный JWT), 403 (нет полномочий), 404 (чужой/недоступный персональный объект), 400 (неверные поля), 409 (конфликт номера/состояния). ProblemDetails с постоянным `code` и `traceId`, без `idempotency-result`.
- PUT/PATCH/DELETE существующих изменяемых настроек — strong ETag/If-Match: отсутствие 428, устаревший 412. Экономические операции и удаление выписки If-Match не требуют (другая защита).
- Списки: `items + nextCursor`, default 50, max 100; история append-only не пропускает/не дублирует существовавшие записи при новых вставках.
- Live leaderboard — top N и отдельное `own` место. GET не инициирует экономику/финализацию/выдачу ссылки. Export создаётся 201; статус читается стабильным DTO; download link — отдельный ресурс.
- Для каждой (method, route, status, media type) — одна определённая схема; коллекции типизированы (без `Page.items: object`); обязательные/nullable поля, ограничения и примеры описаны.

## 8. Авторизация (D207)

- **Проверка компании и области для каждого входного ID:** `employee/wallet/resource` — принадлежность компании; `campaign/resource` — набор кампании; `milestone/achievement` — компания; `integration/purchaseSystem` — компания; заказ выписки — заказчик/компания. Чужой ID → 404.
- **Актуальные права перед replay:** отзыв grant/владения и активность проверяются до возврата сохранённого результата (B05).
- **Service** не может вызывать персональные сценарии (кошелёк/выписка сотрудника); только разрешённые grants (T03).
- **Владелец** не получает полный кошелёк участника (B03d); **Admin** не скачивает чужой заказ экспорта (B37a) — роль Admin даёт права на данные своей компании, но заказчик выписки — конкретное лицо.
- Проверки реализуются в Application-входах (не только в middleware) и сохраняются при вызове из Worker и functional integration (D207/D211).

## 9. Нагрузка и поставка (T09–T10)

Профиль: 10 000 сотрудников (основная компания) + 100 (другая); 3 ресурса, 10 кампаний × 10 заданий; 100 000 исторических событий и 100 000 движений; seed 42, подготовка через валидируемые use cases/batch (без невозможных INSERT). Ресурсы: два API по 1 CPU/1 GiB за балансировщиком; PostgreSQL 2 CPU/4 GiB; два worker суммарно 1 CPU/1 GiB; Valkey 0,5/0,5; S3 1/1; генератор отдельно.

Открытая нагрузка: 100 req/s, 60 с прогрев, 300 с измерение; состав 50/25/10/10/5% (каталог/кошелёк/live leaderboard/новые события/списания); средств достаточно; доля завершений сообщается отдельно. Цели: p95 чтений ≤200 мс, записей ≤500 мс; p99 ≤1 с; корректных ответов ≥99,5%; без потерь/дублей/перерасхода. Доп. RPS 250/500/1000 — не заменяют основной профиль. Отчёт: planned/sent/completed RPS, goodput в 1 с, p95/p99 по видам, таймауты, ошибки, dropped, CPU/RAM, задержки БД; проверяется итоговое бизнес-состояние. Отдельные проходы: Valkey off 30 с, S3 off 30 с, один API off 10 с; PostgreSQL off — безопасный 503 и восстановление (не «бизнес-доступность»).

На этапе реализации потребуются Compose, команды миграций/bootstrap/tests/load, `.env.example` без секретов, README ≤ 2 страниц, примеры Employee/Admin/Integration, версии и сырые результаты. **Сейчас — спроектирован контур, а не заявлены проведённые нагрузочные/runtime-проверки.**

## 10. Тестирование (T08/D211)

- **Unit** — чистые правила, точные суммы, календарные границы (домен).
- **Functional integration** — PostgreSQL 17/Valkey 9/S3: Arrange/Act/Assert через **штатные use cases или HTTP**, без прямых DbContext/DbSet/SQL/NpgsqlConnection и без обхода validation/authorization; управляемое время (`TimeProvider`), ограниченные ожидания, реальная конкуренция.
- **HTTP/contract** — штатные JWT, middleware, ETag, статусы, схемы.
- **Persistence/migration** — выделенная группа, где прямой EF/SQL допустим (создание/удаление БД, миграции — не запрещённая бизнес-подготовка).
- **Architecture** — зависимости и запрещённые обращения; **отрицательный контроль**: компилируемое нарушение зависимости должно вызывать падение; для смысловых проверок правильный вариант проходит, ошибочный исполняется и падает по нужному правилу (ошибка сборки ≠ обнаружение бизнес-дефекта).
- **E2E** — два процесса, конкуренция, рестарты, отказы, экспорт.
- Expected выводится из бизнес-правил, не из production-калькулятора. Test-only auth handler не заменяет проверки JWT. Произвольный Sleep не заменяет синхронизацию.
