# stage-3 — Motiva: план разработки и проверок

Входы: бизнес-задание v3.0 (`01_BUSINESS.md`, `B01–B37`, `E01–E12`), инженерные условия (`02_ENGINEERING.md`, `T01–T10`), договор JWT (`03_AUTH.md`), утверждённые `stage-1.md` (анализ требований, сценарии `S1–S10`, `B1–B10`), `stage-2.md` (архитектура, модель, протоколы, `openapi.yaml`), `.editorconfig`.

Этот этап — декомпозиция утверждённого решения на исполнимые проверяемые задачи. Код приложения не пишется, архитектура заново не проектируется, оценки в часах не выдумываются. Остановка — до реализации.

---

## 0. Входы и реальные пробелы входа

Используется весь согласованный общий набор этапа 2: стек (§1), договор JWT (§2, `03_AUTH.md`), модель данных (§3, D210), механизмы инвариантов и протоколы (§4, D201–D203), повторы/отмены/числа (§5), кеш/экспорт/надёжность (§6, T06–T07/D208/D209), REST (§7), авторизация (§8, D207), нагрузка/поставка (§9, T09–T10), тестирование (§10, T08/D211).

**Реальные пробелы входа (зафиксированы отдельно, не замалчиваются):**

## 2. Порядок реализации и обоснование зависимостей

Фазы соответствуют запросу: **окружение/JWT/миграции → первый вертикальный сценарий → рисковые инварианты → остальные сценарии → отказы и нагрузка.**

| Фаза | Задачи | Смысл |
|---|---|---|
| A. Фундамент | TK01→TK02→TK03→TK04 | Стенд и договор. Без рабочего JWT и миграций ни один вертикальный сценарий не исполняется. Bootstrap (TK04) зависит от миграций (TK03). |
| B. Вертикаль S1 | TK05→TK06→TK07→TK08 | Первый рабочий сквозной сценарий от HTTP-события до кошелька (S1/E01) и ближайшие отказы (S2/E02/E03). Доказывает, что протокол приёма, бюджет↔кошелёк и идемпотентность работают на реальном стеке. |
| C. Рисковые инварианты | TK09→TK10→TK11 | Самое дорогое в исправлении: бессрочная идемпотентность операций, конкуренция за остаток, одна успешная отмена. Выполняется сразу после вертикали, пока протокол свежий. |
| D. Остальные сценарии | TK12→TK13→…→TK19 | Механики по мере зрелости: периоды, архив, доступ/тенант, вехи/достижения, челлендж/рейтинг/кеш, выписка, ручное начисление, аудит. |
| E. Отказы, нагрузка, поставка | TK20→TK21→TK22 | E2E и деградации, затем нагрузка на стабильном стенде, затем упаковка. |

**Обоснование только нетривиальных зависимостей:**

- **TK07 зависит от TK06, а не от TK05 напрямую только через порты.** Вертикаль S1 бессмысленна без возможности создать кампанию/задание/бюджет и опубликовать. TK06 даёт штатный (не SQL) путь подготовки бизнес-данных, который затем используется и в тестах всех последующих задач (§3). Это согласуется с запретом обходного SQL в Arrange (T08).
- **TK09/TK10/TK11 стоят сразу после вертикали (фаза C), а не в конце.** Это рисковые экономические инварианты (повторы, перерасход, одна отмена); их исправление в конце обошлось бы переделкой протокола приёма. Интеграционные тесты здесь не откладываются — они часть задач.
- **TK16 (рейтинг/кеш) и TK17 (выписка) зависят от TK08/TK07**, потому что счёт челленджа строится на `credited_increase` приёма события, а выписка — на `wallet_movement`, создаваемых начислением/списанием.
- **TK20 (E2E) зависит от TK09/TK16/TK17**: восстановление после рестарта требует проверенной идемпотентности (TK09), финализации (TK16) и снимка/cleanup (TK17). Только после этого имеет смысл нагрузка TK21 на стабильном стенде.
- **TK21 → TK22**: нагрузка прогоняется до упаковки, чтобы в поставку попали фактические результаты (T10).

Циклов в графе зависимостей нет (все рёбра направлены от более ранних задач к более поздним). Несогласованных зависимостей нет (см. §6).

| **End-to-end** (отдельные процессы) | Два API + два worker, конкуренция, рестарты, отказ кеша/S3/API/PG, экспорт и неизменяемый снимок, защита байтов от перезаписи. | TK16, TK17, TK20 |

**Способ подготовки бизнес-данных без прямого DbContext в функциональных тестах.** Интеграционный тест-хост (TK05) работает через **composition root** реального приложения: Arrange вызывает штатные application use cases (компания → Admin → сотрудники → ресурсы → кампания → стрим → задания/награды → вехи/челлендж → выделение бюджета → публикация), либо через тот же путь, что и HTTP (для HTTP/contract-группы — реальные подписанные токены из `auth/jwt.py`). Прямой `DbContext`/`DbSet`/SQL/`NpgsqlConnection` в fixtures и helpers запрещён (T08). Допустимый прямой EF/SQL — только в группе migrations (создание/удаление тестовой БД, применение миграций). Для нагрузочной подготовки (T09) — те же валидируемые use cases/batch с seed=42, без «невозможных» INSERT. Тест-хелпер-строитель сценария (`ScenarioBuilder`) инкапсулирует только легальные вызовы use cases, что и есть «подготовка данных».

**Управление временем.** Внедряется `ITimeProvider` (обёртка `TimeProvider`) как единственный источник системного момента `accepted_at`/commit (B14, T05). В функциональных тестах используется детерминированная подменяемая реализация, которую тест устанавливает и продвигает на нужные моменты; календарь и границы периодов/челленджа/финализации считаются от него через `ICompanyCalendar`. Production-HTTP переключатель времени отсутствует (T05). Ожидания на границах (период, полуночь, интервал челленджа, момент фиксации снимка) задаются явным продвижением «часов», а не Sleep.

**Синхронизация конкуренции.** Реальная конкуренция выполняется на реальном PostgreSQL (T06): N параллельных вызовов (use cases/HTTP) запускаются с барьером/`Task.WhenAll` для максимального пересечения; корректность обеспечивается `READ COMMITTED + SELECT … FOR UPDATE` по единому порядку захвата `stage-2 §4.7`, а не process-lock или Valkey-lock. Утверждаются инварианты-исходы (одна posted одна declined; остаток 3, не −4; бюджет 0, не −10; одна успешная отмена), а не конкретный победитель (порядок очереди не требуется — B20f). Неопределённый commit и конкурентный повтор обрабатываются ограниченным ожиданием/повтором в рамках общего deadline (§6.4); произвольный Sleep не используется как синхронизация (T08).

## 5. Definition of Done

Выполняется после каждого инкремента (фаза) и финально перед сдачей. Команды — проектные (фактические фиксируются в TK01), exit codes и сырые результаты прикладываются к сдаче.

**Команды запуска/проверки:**
- Сборка и формат: `dotnet build Motiva.sln` (0 warnings-as-errors по `.editorconfig`); `dotnet format Motiva.sln --verify-no-changes` — чист.
- Тесты по слоям: `dotnet test Motiva.Tests.Unit`, `Motiva.Tests.Integration` (функциональная/HTTP/контрактная группы), `Motiva.Tests.Architecture`, группа persistence/migrations, E2E (отдельные процессы). Зелёный набор не доказывает правильность ожиданий — ожидания проверяются независимо от production-калькулятора (T08).
- Архитектура: отрицательный контроль — компилируемое нарушение зависимостей падает; смысловые правила проходят/падают по нужному бизнес-правилу.

**Миграции:** применяются на PostgreSQL 17 на чистой БД и на переходе от предыдущей миграции (`dotnet ef database update`); constraints/триггеры/partial unique index и expression index подтверждены тестами TK03.

**Контракт:** каждая (method, route, status, media type) имеет одну определённую схему по `openapi.yaml`; экономический отказ — 201/`OperationOutcome{status:declined}`, не ProblemDetails; статусы 400/401/403/404/409/412/428 по T04; ETag/If-Match для изменяемых настроек; повторы по T05 (бессрочный бизнес-номер + транспортный ≥24 ч); отмена по D202 (одна успешная, 409 на конфликт состояния).

**Аудит:** изменения прав/настроек/бюджета имеют `audit_entry` с инициатором и временем; `GET audit` доступен Admin; секреты/JWT/signed URLs не логируются.

**Восстановление и отказы:** E2E — два процесса, рестарты, отказ Valkey (PG-fallback), S3 (экономика работает, задачи повторимы), один API; PostgreSQL off → ограниченный 503 и безопасное восстановление; worker crash после upload → CAS Ready; cleanup ≤10 мин; повтор после commit/рестарта не дублирует эффект (T06/T07).

**Нагрузка:** профиль seed=42 (10 000+100, 3 ресурса, 10 кампаний × 10 заданий, 100 000 событий и движений); 100 req/s (60 с прогрев + 300 с), состав 50/25/10/10/5; p95 чтения ≤200 мс, записи ≤500 мс, p99 ≤1 с, корректных ≥99.5%; без потерь/дублей/перерасхода; выписка 100 000 строк ≤120 с; финальный рейтинг ≤5 с; отдельные проходы деградаций; два конкурента за остаток. Отчёт с planned/sent/completed RPS, goodput, p95/p99, таймаутами/ошибками/dropped, CPU/RAM/задержками БД и проверкой итоговых бизнес-состояний.

**Сдаваемые доказательства (T10):** Compose, команды миграций/bootstrap/тестов/нагрузки, `.env.example` без секретов, README ≤2 страниц, примеры запросов Employee/Admin/Integration, зафиксированные версии/образы, lock-файлы, актуальные документы этапов и связь требование→реализация/тест, commit + фактические команды/exit codes, сырые результаты тестов и нагрузки, список ограничений; неисполненное помечено «не проверено»; требования/тесты не переписываются под дефект.

**Блокирует следующий инкремент (что нельзя пропускать):**
- TK01 (сборка/формат/стенд) и TK02 (JWT-договор) — без них не исполняется ни одна последующая проверка (блокирует все).
- TK03 (миграции) — без схемы не работает ни один vertical slice.
- TK07 (протокол приёма) — база всех экономических сценариев; блокирует C/D.
- Фаза C (TK09–TK11) обязательна до фазы D: недоказанная идемпотентность/одна отмена делает более поздние сценарии ненадёжными.
- TK20 (E2E/отказы) обязателен до TK21 (нагрузка на стабильном стенде).
- Пропуск какой-либо проверки DoD-фазы блокирует переход к следующей фазе.
