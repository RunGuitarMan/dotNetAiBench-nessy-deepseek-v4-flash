**I201 — strong ETag набора grants в контракте чтения.**
- Исходное противоречие: `replaceIntegrationGrants` (PUT `/api/v1/integrations/{integrationId}/grants`) требует `If-Match` (428/412), но контракт чтения `listIntegrationGrants` (GET) не описывает получение ETag; без этого условие 428/412 невыполнимо и не тестируемо по контракту.
- Требование: документировать выдачу сильного ETag текущего набора grants в ответах чтения и успешного изменения (включая пустой набор); сохранить 428/412 и актуальность прав (D207).
- Точная поправка (внесена в `openapi.yaml`): к ответу `_PageIntegrationGrant` (GET 200 и PUT 200) добавлен заголовок ответа `ETag` — strong ETag текущего набора grants (I201), обязателен для `If-Match`, выдаётся и для пустого набора.
- Источник: этап 2 (`stage-2 §7`, §7.2 grants PUT). Статус: внесено в `openapi.yaml` (внешняя нормализация H3); учтено в TK05 (HT-21).

**I202 — значение и жизненный цикл `CatalogItem.asOf`.**
- Исходное противоречие: в `openapi.yaml` описание `asOf` — «момент заполнения кеша каталога», что противоречит `stage-2 §6.1`: момент фиксируется **перед началом чтения данных из БД** и **не обновляется при записи в кеш**; срок свежести не начинается заново после позднего заполнения.
- Требование: согласовать описание OpenAPI с `stage-2 §6.1`; `asOf` отражает начало чтения данных, не момент записи в кеш.
- Точная поправка (внесена в `openapi.yaml`): описание `CatalogItem.asOf` — «момент, зафиксированный перед началом чтения данных из БД; не обновляется при записи в кеш; срок свежести не отсчитывается заново после позднего заполнения (stage-2 §6.1, I202)».
- Источник: этап 2 (`stage-2 §6.1`, T06/D209). Статус: внесено в `openapi.yaml` (внешняя нормализация H3); учтено в TK20 (FT-200/201/204).

## 1. Тестовая управляемость и схема Test ID

**Слои тестов (T08/D211) и префиксы Test ID:**
- `UT-##` — Unit (чистые правила, точные суммы, границы календаря; doubles допустимы).
- `FT-##` — Functional integration: реальные PostgreSQL 17/Valkey 9/S3; Arrange/Act/Assert через штатные application use cases или HTTP; **без** DbContext/DbSet/SQL/NpgsqlConnection в Arrange, включая fixtures/helpers; не обходит validation/authorization pipeline.
- `HT-##` — HTTP/contract: реальные подписанные JWT, middleware, сериализация, статусы, ETag/If-Match, схемы.
- `PT-##` — Persistence/migrations: прямые EF/SQL допустимы для mappings, constraints, триггеров, миграций; не заменяют functional integration.
- `AT-##` — Architecture: зависимости и запрещённые обращения; отрицательный контроль (компилируемое нарушение падает; смысловые правила — правильный вариант проходит, ошибочный исполняется и падает по нужному правилу).
- `ET-##` — End-to-end: отдельные процессы, конкуренция, рестарты, отказы, экспорт.

**Управляемость без production-HTTP-переключателя времени (D305):**
- `ITimeProvider` (обёртка `TimeProvider`) — единственный источник системного момента `accepted_at`/commit (B14/T05); в тестах — детерминированная реализация, продвигаемая вручную. `ICompanyCalendar` считает периоды/сезон/челлендж от неё.
- Координация внутренних гонок — **тест-only порт-барьер**: реализация `ITransactionScope`/`IUnitOfWork` (либо выделенный `ITestCoordination`) в composition root теста вставляет барьеры (`SemaphoreSlim`/`TaskCompletionSource`) на фиксированных фазах транзакции (после захвата `FOR UPDATE`-замков, перед чтением снимка, перед commit). Это воспроизводит нужную внутреннюю гонку детерминированно, **не меняя бизнес-протокол и не обходя validation/authorization** (они выполняются внутри use cases независимо от порта). Ожидания ограничены (bounded wait в рамках общего deadline stage-2 §6.4); произвольный Sleep не используется как синхронизация (T08).
- Никакого HTTP-переключателя времени (T05); контроль только через порты и composition root теста.
- **Изоляция параллельных тестов:** каждая функциональная группа работает на отдельной схеме/БД; физическая изоляция через уникальные идентификаторы; конкурентные тесты не разделяют состояние.

### 3.2 Минимальный штатный путь подготовки данных для S1 (D302)
Без скрытого SQL, обхода авторизации и нереализованных helpers — только штатные use cases/HTTP, валидируемые на каждом шаге. Для каждого шага указана операция и задача, обеспечивающая её готовность:
1. bootstrap → компания + активный Admin (TK04, доверенные use cases);
2. `createResource(A)`, `createResource(B)` (TK04);
3. `createEmployee(masterId, теги, активен)` → создаётся ровно один кошелёк (TK04);
4. `createAchievement` (определение для вехи) → `createCampaign(draft)` → `createStream` → `createTask(+ награды 10A+2B, цель 3, очки 5)` → `createMilestone`/`createChallenge` (TK06);
5. `allocateBudget(A=10)`, `allocateBudget(B=2)` — только Admin (TK06);
6. `publish` — атомарный переход (TK06);
7. `createIntegration` (TK05) + `PUT grants {progress по кампании}` (endpoint TK05) — **progress-grant создаётся только после существующей кампании (шаги 4–6)**, т.к. область `progress` требует `campaign_id` (D210);
8. `POST /events` с `sourceEventNo` (TK07);
9. `GET progress`/`GET wallet`/`GET budget` — read-back результата (TK07).

Приёмка шагов 8–9 не требует ещё не готовых возможностей: событие использует progress-grant (шаг 7), read-back — часть инкремента TK07.

### 3.3 Обоснование нетривиальных зависимостей
- **TK07 ↔ TK06 и read-back:** вертикаль S1 требует готовой кампании/задания/бюджета/публикации (TK06) и интеграции с progress-grant (TK05). Progress-grant создаётся после существующей кампании (см. §3.2, шаг 7). Приёмка TK07 читает результат через read-back (`GET progress/wallet/budget`), включённый в сам инкремент TK07, поэтому FT-53/FT-57 не зависят от TK08: progress/completion/очки/достижения/решение/движения читаются штатными операциями TK07 (D302).
- **TK05 — области grant (D302):** валидация областей progress/accrual/spend — unit-правило (UT-05), кампании не требует; spend-grant создаётся функционально на purchase_system+resource (HT-21). Функциональное применение progress/accrual/spend grants — в TK07 (событие), TK10 (начисление), TK09 (списание), где кампания/ресурс/система уже готовы. Отказ по невыданному/отозванному grant — FT-24 (TK07), FT-76 (TK09), FT-85 (TK10).
- **TK09/TK10 зависят от TK07/TK08:** списания и начисления оперируют балансом/бюджетом, созданными начислением в S1; чтение результата — через read-back TK07 и TK08.
- **Влияние ручного начисления на достижения/рейтинг (D302):** FT-83 (TK10) проверяет неизменность прогресса/завершений/очков; влияние на достижения вынесено в TK15 (FT-135), на счёт челленджа — в TK16 (FT-146), где эти механики уже реализованы. TK15/TK16 зависят от TK10 (операция ручного начисления доступна), обратной зависимости (TK10←TK15/TK16) нет — фазовый запрет снят.
- **TK11 зависит от TK09/TK10/TK08:** тест E06 (отказ траты → начисление → повтор) требует проведённого начисления (TK10) и списания (TK09); чтение движений/операций для Assert — через TK08.
- **TK12 зависит от TK11/TK08:** проверки отмены (E07/E08/B5/D202) опираются на проведённые начисления/списания и на идемпотентность номеров отмены (TK11); чтение движений/операций — через TK08.
- **TK22 (транспортная идемпотентность)** выполняется после создающих задач и экспорта (TK17): консолидирует T05-проверки; базовые проверки включены и в сами создающие задачи (HT-13/HT-33).
- **JWT: TK02 проверяет только крипто-договор** (подпись/claims). Проверки бизнес-прав (заблокированный, отозванный grant, replay) размещены в TK11/TK14/TK18, где эти возможности уже реализованы (D302).
- **Коррекции и история:** экономический FT-103 готов в TK12; влияние отмены на достижения проверяет FT-136 в TK15, на live/final рейтинг — FT-147/FT-148 в TK16. TK15/TK16 зависят от TK12; обратного ребра нет. TK14 зависит от готовых трат/начислений/отмен и календарных проверок. TK17 зависит от TK12 для смешанных историй и позднего commit, TK18 — от TK17 для доступа к выпискам, TK20 — от TK18 для каталога.
- **Принцип:** для каждой приёмки операции Arrange и Assert перечислены в §2 и §3.2; каждая операция доступна к моменту Done своей задачи (ранний wallet — в TK04, бюджет/аудит — в TK06, read-back события/движения — в TK07, расширенная история — в TK08, лидерборд — в TK16).

| TK23–TK25 | Два API/worker, отказы и перезапуски, затем нагрузка и clean start | Уже готовые публичные операции, файлы, health/метрики/сырые отчёты. |

Составной B-пункт может завершаться несколькими проверками на разных инкрементах; каждая названа явно. Фаза C блокируется только Done TK09–TK12, а последующие регрессии B21/B26 в TK15/TK16 блокируют фазу D. Они обязательны для итоговой сдачи и не объявляются пройденными в TK12.

## 4. Спецификации воспроизводимых ключевых тестов (D305)

Формат каждого: данные → штатная подготовка → точка остановки/сбоя и порядок освобождения → синхронизация и лимит ожидания → предвычисленный результат → наблюдаемый Assert → запрещённые эффекты → задача первого прохождения. Управляемость — через §1 (ITimeProvider + порт-барьер), без HTTP-переключателя времени и без изменения бизнес-протокола.

### 4.1 Конкуренция и целостность
**FT-53 (E04 — две награды за последний бюджет).**
- Данные: бюджет A=10; один сотрудник, кошелёк A=0; два задания в разных стримах одной кампании без челленджей, у каждого цель 3, очки 5, награда 10A. Два события по +3. Так общим конфликтующим ресурсом служит бюджет, а не строка прогресса/очков/челленджа.
- Подготовка: штатный путь TK04/TK06 (2 задания, budget A=10, publish); два интеграционных события с разными `sourceEventNo`.

Барьер не ждёт прибытия обоих участников после эксклюзивного замка. Координация до/после запроса замка подтверждает перекрытие; общий исход не зависит от имени победителя.

- Запрещено: бюджет −10; потеря завершения; повторная выдача.
- Задача: TK07 (FT-53).

**FT-70 (E05 — две траты).**
- Данные: кошелёк A=10; две траты по 7 с разными бизнес-номерами. Первая удерживается после захвата wallet_balance, вторая начинает ожидать этот замок; затем первая освобождается до commit. Сигналы порта и ожидание ≤10 с, без барьера после замка для обоих участников.

**FT-103 (D202 — одна успешная отмена; корректный oracle по B18/B19/B26).**

- **Шаг 7** — новая отмена того же уже отменённого оригинала с номером N3 → 409, движений нет, результат N2 не меняется. Конкурентное получение единственного успеха проверяет FT-104 на отдельном исходном состоянии до успешной отмены.

При промежуточном выделении бюджета в шаге 4, до начисления, кошелёк остаётся 10A+1B: отдельная попытка N1b также declined, бюджет B остаётся 1. **FT-104 (одна успешная отмена при конкуренции, TK12).** Для двух попыток с разными номерами — отдельный setup: кошелёк 10A+2B, исходная награда ещё не отменена, бюджеты 0. Первая попытка удерживает original_operation до commit, вторая до освобождения пытается получить этот замок. Для возврата траты — исходно трата 7 и кошелёк 3: один posted, второй 409, итог 10; бюджет не меняется. Ожидания ≤10 с, обе попытки не ждут друг друга внутри эксклюзивного замка.

### 4.2 Граница соревнования
**FT-149 (B33 — гонка события и финализации на границе интервала).**
- Данные: челлендж по стриму, интервал `[start, end)`, `start=2026-06-01T11:00:00Z`, `end=T=2026-06-01T12:00:00Z`, ε=1 мс; кампания действует весь июнь. Участник P один, цель задания 100, предыдущее событие +50 принято в 11:30Z; S0=50. Новое событие E: +10, остаток цели 50 → credited=10. Каждое расписание использует отдельный setup.
- Штатная подготовка: TK06 (задание/стрим/челлендж, publish), TK05 (интеграция + progress-grant), TK07 (события). Время — через `ITimeProvider` (детерминированно).
- **Сценарий 1** (событие до end, включено): E принимается с `accepted_at = T − ε`, коммит до финализатора; финализатор при `now ≥ T` захватывает `FOR UPDATE` challenge и **отдельным запросом после замка** читает события `start ≤ accepted_at < end` → E включено; итог = 60.
- **Сценарий 2** (событие ждёт замок, не включено): финализатор держит `FOR UPDATE` challenge; E стартует до T, блокируется на замке и получает `accepted_at ≥ T`; после коммита финализатора E не входит; итог = 50.
- **Сценарий 3** (E уже принято до end, держит замок и ещё не закоммичено; финализатор после end ждёт E — различает ошибочную финализацию):
  - E принято с `accepted_at = T − ε`, счёт участника в транзакции E обновлён, но транзакция E **не закоммичена** и удерживает `FOR UPDATE` на строке challenge.
  - Финализатор запускается при `now = T`, пытается `FOR UPDATE` challenge → **блокируется за E**.
  - Порядок освобождения: сначала коммит E, затем финализатор получает замок и **после ожидания замка** отдельным запросом читает события `start ≤ accepted_at < end` → видит закоммиченное E → итог = 60.
  - Ключевой смысл: если реализация взяла снимок (REPEATABLE READ) **до ожидания замка**, она увидит счёт без E → итог 50; проверка требует итог 60 и тем самым **обнаруживает потерю события** при снимке, полученном до ожидания замка.
- Точки координации: сигнал удержания E после записи и до commit, сигнал попытки финализатора взять challenge с подтверждением ожидания за E; E освобождается после этого, а не по таймеру. Затем сигнал захвата финализатором и его чтение. Отдельные точки используются в обратном расписании 2. Ожидание ≤10 с (stage-2 §6.4), нет барьера, требующего одновременно держать один эксклюзивный замок.
- Наблюдение: `getChallenge` показывает state=final; `getLeaderboard`/`getOwnRating` дают P со счётом 60/50/60 и местом 1. `getChallenge` не обязан возвращать счёт. Внутренние event/challenge_score напрямую не читаются. Для сценария 2 E запускается в T−1 мс и останавливается перед попыткой взять challenge (accepted_at ещё не фиксировался). Часы переводятся в T, финализатор захватывает challenge и останавливается перед commit. E освобождается и ожидает этот замок; затем финализатор коммитится. E получает accepted_at=T только после захвата замка. Финализатор не запускается до конца интервала.
- Результат: 1→60; 2→50; 3→60. Повтор E на следующий день не меняет final. В этом setup цель ещё не достигнута и награды нет: влияние отмены награды на final проверяется отдельным FT-147/FT-148 с завершённым награждённым заданием.
- Запрещено: потеря события с `accepted_at < end` (в т.ч. из-за снимка до ожидания замка); пересчёт итога после final; попадание в итог события с `accepted_at ≥ end`.
- Задача: TK16 (FT-149).

### 4.3 Снимок выписки (B36)
**FT-155 (снимок при первом успешном начале формирования, не при заказе).**
- Данные: движение M1 до заказа; движение M2 между заказом и началом формирования.
- Подготовка: заказ выписки (state=pending); затем движение M2; затем worker начинает формирование.
- Результат: состав фиксируется при первом успешном начале формирования — включает M2, зафиксированный в `statement_data`; повторные попытки используют тот же состав.
- Assert (через разрешённые границы): готовый CSV содержит ровно движения состава (M1 и M2), а не только на момент заказа; добавление M3 после фиксации не дописывается в файл.
- Запрещено: состав по времени заказа (а не начала формирования); новые движения в уже зафиксированную выписку.
- Задача: TK17 (FT-155).

**FT-156 (поздний commit с ранним временем движения).**
- Данные: движение с `created_at/occurred_at` раньше снимка, но транзакция коммитится позже начала формирования.
- Точка остановки: барьер приостанавливает списание/начисление перед commit; снимок формируется; затем коммит движения.
- Результат: движение **не** входит в состав (MVCC-видимость снимка, а не только timestamp-фильтр).
- Assert: CSV не содержит это движение; `statement_data` не меняется.
- Запрещено: включение невидимого на момент снимка движения.
- Задача: TK17 (FT-156).

**FT-157 (повтор формирования после crash).**
- Данные: сохранённый состав содержит M1=+10A и M2=−3A, итог по CSV=7A. Worker упал после загрузки объекта, до Ready. До перехвата lease через штатное начисление создаётся M3=+5A, так что текущий кошелёк=12A. Новый worker обязан выпустить прежние две строки M1/M2, сумму 7A и те же байты; M3 в выписку не входит. Это отличает восстановление состава от незаметной пересъёмки.
- Точка сбоя: прерывание worker после upload (E2E), `statement` остаётся `forming` с истёкшим lease.
- Восстановление: другой worker перехватывает по lease, использует тот же `snapshot_id` (состав не переснимается), публикует Ready через CAS (`WHERE state='forming' AND owner_worker_id=:me`).
- Результат: готовый файл идентичен; повтор формирования не переснимает состав.
- Запрещено: пересъёмка состава; публикация Ready на утраченном владении; Ready на удалённую выписку.
- Задача: TK17 (FT-157), TK23 (ET-восстановление).

**FT-159 (неизменность готовых байтов).**
- Результат: объект детерминированного ключа `snapshot_id`; conditional write (`put-if-absent`) не перезаписывает существующий проверенный объект; при восстановлении — проверка существования + content-md5.
- Assert: повторная запись в тот же ключ не меняет байты; скачанный файл совпадает с ожидаемым содержимым (проверяется по разрешённым границам, не по внутреннему `snapshot_id`).
- Запрещено: перезапись готового объекта; чтение частично записанных байтов.
- Задача: TK17 (FT-159), TK23 (E2E).

## 5. Оба механизма идемпотентности (D303)

### 5.1 Бессрочные бизнес-повторы (B16/B24) — TK07 (события), TK11 (операции)
Область события `(company, source_id, source_event_no)`; операций `(company, initiator_key, kind, source_no)`. Повтор возвращает прежний результат из `operation_request`, а не пересчитывает; текущие права проверяются до replay (TK11/FT-92/FT-93); изменённые существенные данные → 409 (FT-91). `Idempotency-Key` экономических операций — бизнес-номер (D201), хранение бессрочно.

### 5.2 Транспортная идемпотентность (T05) для настроек, заказов экспорта и ссылок — TK22 (полный матрикс), базово в создающих задачах
Scope: `(company, проверенный инициатор, операция/целевой ресурс, ключ)`. Хранение ≥24 ч. Один заголовок без дублирующего ключа.

## 6. Эксплуатационное покрытие (D304)

### 6.1 Кеш — TK20
- Каталог: TTL/свежесть ≤30 с; ключ `catalog:{company}:{season}`; `asOf` фиксируется перед чтением БД и не обновляется при записи (I202). Чтение: возраст >30 с → miss → перечитать, перезаполнить. Запись: write-if-`asOf`-newer (атомарно), поздний fill не продлевает жизнь старому снимку; просроченное/повреждённое значение → miss; отказ Valkey → ограниченное ожидание + PG fallback (FT-200/201/203/204/206).
- Live leaderboard: свежесть ≤5 с; ключ `lb:{challengeId}:top:{limit}`; `asOf` в ответе; финальный итог — авторитетные неизменяемые `challenge_score`, не кеш (FT-202).
- Фильтрация прав — из актуального источника (D209), кеш не источник устаревших прав (HT-205).
- Кеш не используется для денег/прав/активности (T06).

### 6.2 Readiness/liveness, логи, метрики — TK21
- Readiness отражает возможность основной работы; liveness не падает только из-за внешней зависимости (ET-210/211).
- Structured logs, correlation/trace ID (ET-212); метрики задержек/ошибок/повторов/состояния очереди (ET-213).
- Не логировать токены, ключи и signed URLs (ET-214); секреты не в `.env` и не коммитятся.

### 6.3 E2E отказы и восстановление — TK23
- Два API + два worker; корректность не зависит от process-local/Valkey-lock (сериализация в PostgreSQL).
- Worker crash после upload → CAS Ready; перехват по lease с тем же `snapshot_id`; удаление↔Ready взаимоисключаются (CAS `state='forming'`), готовый объект не воскрешается после deleted.
- Cleanup объектов/незавершённых загрузок со `state=deleted` ≤10 мин после восстановления зависимостей; гонка cleanup↔Ready исключена (cleanup только после необратимого deleted).
- Отказ S3 → экономика работает, экспорт повторим; Valkey off → PG fallback; PostgreSQL off → ограниченный 503 и безопасное восстановление; повтор после commit/рестарта не дублирует эффект.
- Срок download-link ≤60 с; повтор ключа возвращает ту же ссылку; удаление запрещает новые ссылки немедленно.

### 9.1 DoD
**Команды:** `dotnet build Motiva.sln` (чисто, 0 новых warnings); `dotnet format Motiva.sln --verify-no-changes`; `dotnet test` по слоям (Unit/Integration/HTTP/Architecture/persistence/E2E); `dotnet --info` (G1). Зелёный набор не доказывает правильность ожиданий (T08).

**Контракт:** одна схема на (method, route, status, media type) по `openapi.yaml`; экономический отказ — 201/`OperationOutcome{status:declined}`; статусы 400/401/403/404/409/412/428; ETag/If-Match для настроек (включая I201 для grants); повторы по T05 (бессрочный + транспортный ≥24 ч); отмена по D202.

**Нагрузка (T09):**
- Открытая модель нагрузки; профиль seed=42 (10 000+100 сотрудников, 3 ресурса, 10 кампаний × 10 заданий, 100 000 событий и 100 000 движений); подготовка валидируемыми use cases/batch вне измерения, без «невозможных» INSERT.

- Адаптер маршрутов утверждённого OpenAPI (не подмена на лёгкие аналоги).
- Ресурсы стенда: 2 API по 1 CPU/1 GiB, PG 2 CPU/4 GiB, 2 worker суммарно 1 CPU/1 GiB, Valkey 0.5/0.5, S3 1/1; генератор отдельно.

План не является отчётом об исполненной реализации. Build, миграции, runtime-тесты и нагрузка должны выполняться на этапе 4 с сырыми доказательствами.
